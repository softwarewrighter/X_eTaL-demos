consider X_eTaL.  What amazing, topical, visual demos could we add?

Given where X_eTaL is heading—typed arrays, concise APL-like composition, readable pretty-printing, and a visual execution/debugger—I think the demo suite can become a major part of the language’s identity.

The sweet spot is:

small X_eTaL program → visually striking result → step through the array transformations → reveal something technically interesting.

That is particularly timely because current ML work is heavily interested in sparse MoE routing, interpretability, state-space models, world models, multimodality, and small/efficient models. For example, 2026 ICML work is explicitly studying MoE experts as interpretable computational units, while other current work examines routing discontinuities and alternative routing formulations. World models and state-space models are similarly active areas.

1. Reaction-diffusion: probably the next killer demo
5

This may actually be a better language demonstration than Life.

Implement the Gray-Scott reaction-diffusion equations on a 2-D array.

You start with something like:

U V

two matrices representing chemical concentrations.

Each frame conceptually does:

laplacian(U)
laplacian(V)

dU = Du*lap(U) - U*V*V + feed
dV = Dv*lap(V) + U*V*V - kill

The browser shows a beautiful continuously evolving organic texture.

Why X_eTaL wins

The important operation is fundamentally:

apply the same local stencil over an entire rank-2 array.

So the visualizer can show:

input array
    ↓
shift north
shift south
shift east
shift west
    ↓
weighted sum
    ↓
laplacian
    ↓
new array

Click any pixel and show its neighborhood and calculation.

That makes the X_eTaL execution model visible.

2. MoE Routing Microscope

This one fits unusually well with your other work.

Imagine 16 little expert boxes:

 E0  E1  E2  E3
 E4  E5  E6  E7
 E8  E9 E10 E11
E12 E13 E14 E15

Enter:

The quick brown fox jumps over the lazy dog.

Tokens flow across the screen.

For each token X_eTaL computes something conceptually like:

scores ← token × router_weights
experts ← top 2 scores

Then animate:

"brown" ───────→ E3
        └──────→ E11

while displaying the routing vector:

[.02 .01 .04 .61 .03 ... .21 ...]
The really interesting experiment

Have a slider perturb the token embedding:

x
x + ε

and display where the selected expert suddenly changes.

That's not just pedagogical decoration. Recent work analyzes exactly this property: sparse top-k routing creates discontinuity boundaries where very similar inputs can select substantially different experts.

So you could visually show the expert decision regions.

That's a terrific X_eTaL demo because it combines:

array programming
modern ML
your MoE work
interpretability
an actual current research question

And current interpretability research suggests experts can exhibit fairly fine-grained computational specialization rather than merely representing broad subject domains.

8. Tiny world model

World models are particularly topical in 2026: they're being investigated across robotics, embodied AI, autonomous driving, video generation and planning.

But don't try to make an enormous generative-video model.

Make the world's state an array.

For example:

┌──────────────┐
│       ●      │
│              │
│   ███        │
│______________│
└──────────────┘

A ball moves under gravity.

The model sees:

frame(t-2)
frame(t-1)
frame(t)

and predicts:

frame(t+1)

Display:

actual future       predicted future

     ●                    ●
                           

       ●                   ●

with error highlighted.

Then let the user alter gravity.

Now the model must discover:

what kind of world am I in?

That's an understandable world model without billions of parameters.

9. N-body gravity

This is another case where array notation can be spectacular.

Put 50 bodies on screen.

For every pair:

Δ ← position_i - position_j
r ← magnitude Δ
F ← mass_i × mass_j / r²

The important thing is that X_eTaL shouldn't write the double loop.

Broadcasting creates the:

N × N × dimensions

pairwise displacement tensor.

Your debugger could literally show this cube.

Then reduce it:

N×N×2
  ↓
N×2

to obtain forces.

That is an unusually good explanation of why array languages are powerful.

A particularly X_eTaL-specific feature

Rather than building these as twelve unrelated demos, I would build one visual execution architecture.

Every demo has four synchronized views:

┌───────────────────────────────────────────────────────────┐
│ X_eTaL source                                             │
│                                                           │
│      expression being evaluated                           │
├───────────────────────┬───────────────────────────────────┤
│ ARRAY / SHAPE         │ VISUAL WORLD                      │
│                       │                                   │
│ [64 64 2]             │        evolving simulation        │
│ [64 64]               │                                   │
│ [64 64 8]             │                                   │
│                       │                                   │
├───────────────────────┴───────────────────────────────────┤
│ execution timeline                                        │
│                                                          │
│  input → each → table → reduce → mask → output            │
│                         ▲                                 │
└───────────────────────────────────────────────────────────┘

Scrub the timeline backward and forward.

Click any operation.

Then show:

value + type + shape + rank + operation + before/after visualization.

That becomes much more than a debugger.

It becomes an array-language microscope.

What I'd build first

I'd make the initial X_eTaL visual gallery around five demos:

Life — composition
Mandelbrot — broadcasting
Reaction-diffusion — stencils and iteration
CNN/MNIST — ML tensors
MoE Router Microscope — modern sparse ML

That creates a really nice progression:

boolean grid
     ↓
numeric grid
     ↓
dynamic numerical system
     ↓
neural network
     ↓
modern sparse model

Then I'd add N-body specifically to demonstrate pairwise broadcasting, attention for matrix/tensor algebra, and the tiny world model as the more ambitious showcase.

The MoE demo in particular could become a bridge between X_eTaL and moe-microscope rather than duplicating the latter: X_eTaL supplies a tiny executable mathematical definition; the microscope shows every intermediate array. Recent work makes that unusually topical because MoE interpretability, routing strategy, efficiency and expert specialization are all active research questions.

The larger design principle I'd adopt is: every X_eTaL demo should contain at least one moment where a conventional programmer sees an animation of a complicated loop nest and realizes that the X_eTaL program describes the whole operation directly as an array transformation. That is the compelling argument for the language, not merely character count.
